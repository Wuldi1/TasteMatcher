# Foundations, entry flows, and home redesign

This is a source-based audit and proposed experience, not a claim of a completed production redesign. References point to current source locations. Visual overflow and usability consequences are reasoned from markup/CSS unless separately verified in the prototype review.

## Design direction

TasteMatcher should feel like a private art advisory with an efficient working desk behind it. Artwork supplies the visual color; interface chrome supplies orientation. Use a warm paper canvas, ink text, restrained borders, and one deep moss accent. Reserve red, amber, and green for meaningful status, always paired with text. Proposed tokens: canvas `#F6F4EF`, surface `#FFFFFF`, ink `#242A25`, muted text `#656C63`, border `#DCDDD5`, accent `#344D40`, accent wash `#E8EDE4`. Verify actual pair contrast in implementation; muted text is for readable secondary content, never disabled-looking primary actions.

Use an editorial serif sparingly for collector-facing display headings and artwork titles; keep navigation, fields, numbers, tables, and operational headings in the existing system/Inter stack. Avoid excessive tracking. Body text should usually be 15–16px, field text at least 16px on mobile. Use 4/8px spacing increments, generous page gutters once (not in shell and page), restrained 8–12px corners, and shadows only when elevation explains a layer.

Artwork grids and detail views deserve more area than decorative dashboard banners. Administrative tables use compact rows, sticky headings when needed, aligned tabular numbers, explicit text statuses, visible sorting/filter feedback, and usable mobile cards or contained scrolling. Primary buttons use ink/moss fill; secondary actions use quiet outlines; tertiary navigation uses text. Destructive controls remain distinct and away from routine choices. Loading buttons retain width and label context.

The guidance follows [Emil's design engineering skill](https://github.com/emilkowalski/skills/blob/main/skills/emil-design-eng/SKILL.md): polish must support a job, frequent interactions must remain fast, motion should use deliberate properties, and review is expressed as Before/After/Why tables. Motion proposals: 120ms press feedback on pointer actions, 160–200ms opacity/transform for contextual panels, no stagger on routine data grids, no animated numbers in work tables, and immediate keyboard/reduced-motion transitions. Do not animate artwork color or distort its aspect ratio. Hover affordances must also exist on focus and touch.

**Layout:** 232px desktop rail with brand, concise grouped navigation, bottom account menu; page header contains breadcrumb/title and local actions. Put gallery scope in the page header only where its data is actually scoped. At tablet widths use a compact rail with accessible tooltips. At mobile widths use a compact top title/account area and stable bottom navigation. Focus-trap any modal navigation or settings sheet, dismiss with Escape, restore focus, and expose `aria-current` on the selected route.

**States:** shell restoration skeleton instead of a blank page while auth initializes; active route; locked eligibility; collapsed rail; expanded More/settings; long account name/email; no submitted proposal; introductory tour that can be skipped and uses viewport-aware positioning. Do not add unread message badges without a reliable unread data source.

## Authentication — `/` and `/login`

**Preserved job:** existing users request and verify a code; unrecognized visitors request either customer or gallery access. Seven phases exist in `components/Login.tsx:10`.

| Before                                                                                             | After                                                                                                                                                     | Why                                                                                |
| -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Centered generic white card on a blue-indigo gradient (`Login.tsx:203`).                           | Desktop split composition: quiet editorial brand/art panel and a restrained sign-in column; mobile becomes a single clean form with compact brand header. | Establishes the art product immediately while keeping the form focused.            |
| Heading stays “TasteMatcher,” with task instructions in small secondary text (`:215`).             | Task title changes: “Welcome back,” “Check your inbox,” “Request collector access,” or “Request a gallery account.” Brand remains separate.               | The current action is the highest-information element.                             |
| UI/API deployment version appears directly under the logo (`:208`).                                | Retain version access in a discreet footer “Version details” disclosure.                                                                                  | Preserves diagnostic utility without making technical metadata part of onboarding. |
| Unknown-account branch presents customer/gallery choices as large stacked actions (`:337`).        | A compact choice screen explains both audiences in plain language, then opens the corresponding existing form with Back.                                  | Clarifies access requests without implying instant account creation.               |
| Success uses nested tinted panels, a large success icon, and repeated paragraphs (`:476`, `:631`). | One calm confirmation with destination email, what happens next from existing copy, and a return-to-sign-in action.                                       | A completed request needs clarity more than visual weight.                         |

**Proposed hierarchy:** brand → specific title and one-sentence explanation → email/code/request fields → one primary action → resend/change/back utility → privacy/terms/version footer. A narrow persistent form column avoids desktop form sprawl. Optional image panel uses approved artwork and visible credit when available, never text baked into an image.

**Interaction:** retain one code field with paste/autocomplete support; show delivery destination and Change email next to it. Do not add a resend countdown unless existing server timing supports it. Errors sit with the relevant input or form and announce through a live region. Move focus to the new phase heading/input after an intentional transition. A 160ms crossfade may bridge pointer-driven phases; keyboard actions and reduced motion are immediate.

**States:** invalid email, code request pending, code verification pending, incorrect/expired code as returned by API, resend success/failure, unknown user, customer/gallery form submission, request success, long email, service unavailable. Do not display a success state merely because a button was pressed in a prototype.

## Onboarding — `/onboarding`

**Preserved job:** collect identity/residence, art interests, collection information/images, and aesthetic description/images. Save progress, skip, revisit answers, and finish into Taster. The existing four-step data contract remains unchanged (`pages/Onboarding/OnboardingPage.tsx:30`, `:45`, `:197`).

| Before                                                                                     | After                                                                                                                                            | Why                                                                                   |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Anonymous progress bar and “Step n of 4” above a centered form (`OnboardingPage.tsx:451`). | Named stepper: About you → Art interests → Your collection → Inspiration. Desktop explanatory side column; mobile compact step label/progress.   | Users understand both the work remaining and the reason for each step.                |
| Choice buttons use `transition-all` and selection is mainly color (`:257`, `:286`).        | Labelled single-choice controls with visible checkmark, border, text, and semantic checked state; instant selection.                             | Clear, fast selection works for color-blind and keyboard users.                       |
| Upload areas say “or drag and drop” but the page has no drop handler (`:320`, `:399`).     | Either implement actual drag/drop with equivalent file-picker access or say “Choose an image.” Show accepted types and progress near the upload. | The affordance must correspond to real behavior.                                      |
| Save/upload failures only reach `console.error` (`:130`, `:188`).                          | Persistent inline error with Retry; retain all local answers and selected file context; “Saved” feedback only after completion.                  | Users know why Next did not progress and can recover without re-entry.                |
| Next saves without setting the submission state for intermediate steps (`:120`, `:138`).   | One guarded saving state per transition, constant button size, no duplicate Next submissions.                                                    | Prevents uncertain progress and competing updates.                                    |
| Existing edit flow looks identical to first-time onboarding (`:65`, `:137`).               | “Your taste profile” heading and context-sensitive Save/Return when editing; preserve original completion semantics.                             | Revisiting preferences should feel like editing a profile, not restarting an account. |

**Proposed page:** brand and “Your taste profile”; left explanation/stepper on wide screens; right form with one clear question per section; image strip directly under upload; footer with Back, Save and continue, and quiet Skip for now. On the final step, “Start discovering” completes the existing save/finalization flow. A mobile action footer may be sticky only if it never covers fields or the keyboard.

**States:** prefilled answers; empty optional field; invalid required field if enforced by current contract; saving; save failure; upload pending/success/failure; completion/finalization failure; skipped profile; completed profile edit. Image previews preserve aspect ratio or label thumbnail crop, and open full-size originals. Do not invent image-removal functionality without confirming an existing persistence path. Keep navigation available after a failed upload.

## Collector home — `/home`

**Preserved job:** resume discovery, maintain taste preferences, inspect saved reactions/proposal progress, share reference art, and converse with a specialist. Available data already includes swipe counts, proposal metadata, shared uploads, and user comments.

| Before                                                                                                                                                      | After                                                                                                                                                  | Why                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Large blue-purple welcome banner, four colored journey tiles, then three icon statistic cards before messages (`CustomerHomePage.tsx:183`, `:194`, `:288`). | Editorial welcome with a single next-step card; compact progress summary; proposal and specialist conversation brought into the first useful viewport. | The page answers “What should I do next?” before showing a dashboard of counts.    |
| Copy says “Train your Model”/“Keep up Model training” (`:232`).                                                                                             | “Discover your taste” and “Keep exploring,” with an honest progress count and eligibility explanation.                                                 | Uses the collector's goal rather than internal model language.                     |
| Share Collection points to `?step=7`, while onboarding accepts only 1–4 (`:255`; `OnboardingPage.tsx:34`).                                                  | Point to actual collection step 3 (and an existing, meaningful anchor if needed).                                                                      | The primary journey action currently returns to Basic Info rather than collection. |
| A fourth journey tile only appears with a proposal, shifting the grid (`:270`).                                                                             | A stable proposal section renders either a meaningful empty state or a compact ready-to-review summary.                                                | State changes are understandable without rearranging navigation cards.             |
| Proposal metadata is a vertical list and absent date can literally read “NaN” (`:331`).                                                                     | Text status with response totals, readable last-updated value or “Not available,” and “Review proposal.”                                               | Clear status and trustworthy missing-value handling.                               |
| Shared gallery can become an unlimited grid before the 500px-high message area (`:355`, `:403`).                                                            | Show a concise reference-art strip with expand/view-all, and a persistent specialist panel beside the main column on desktop.                          | Keeps communication reachable as the collection grows.                             |
| Send/upload failures are console-only; image rendering treats every HTTP URL as an image (`:120`, `:148`, `:425`).                                          | Inline failed-send/upload state preserving draft; render URLs as links unless verified attachment metadata or safe image fallback supports preview.    | Failures are recoverable and ordinary links do not become broken image cards.      |

**Proposed hierarchy:** greeting and concise status → next action (complete profile, continue tasting, review available proposal according to existing state) → compact likes/dislikes/discovery progress → reference gallery; desktop right column contains specialist conversation and proposal summary as appropriate. Mobile order is next action, available proposal, conversation, profile stats, shared references. There is no invented “unread” state, automatic collection attribution, or promised purchase checkout.

**Interactions:** saved likes/dislikes retain existing catalog query destinations. Proposal actions route to the existing proposal. Message composer gains a visible or screen-reader label and labelled attach/send buttons; uploads show progress locally. Smooth-scroll chat only when the user is near the bottom and has not opted for reduced motion; do not interrupt someone reading older messages. “New messages” can indicate newly received entries in this session without inventing backend unread status.

**States:** onboarding redirect; skipped/completed preferences; 0/19/20+ swipes using actual eligibility; no proposal/submitted proposal; no references/many references; no messages/long messages/links/failed media; send/upload error; loading each region without erasing unrelated available content.

**Preserved job:** understand proposal workload, open customer work, check recent artwork intake, and—for owners/admins—inspect seven-day user activity. Dealer proposals are already scoped through `useProposalData`; admin activity has its own gallery selection (`DealerHomePage.tsx:20`, `:34`).

| ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Generic gradient greeting followed by three large counters and four action tiles (`DealerHomePage.tsx:115`, `:126`, `:148`). | “Gallery overview” with compact Total/Pending/Accepted counts and direct Upload/Customers actions; an operational proposal list becomes the main content.                                   | Staff can act on work without scrolling past navigation duplicates. |
| Recent proposal rows identify themselves with raw proposal IDs (`:246`).                                                     | Use customer identity if available from an existing response; otherwise a readable shortened proposal reference with full ID available on detail. Show status and last update consistently. | Makes records scannable without assuming a new customer-lookup API. |
| Conditional View Proposals links to customer `/buying-proposal` (`:184`).                                                    | All staff proposal navigation goes to `/sales` or `/sales/:userId`.                                                                                                                         | Aligns the destination with the staff task.                         |
| Recent upload line uses a single nonwrapping-looking flex row containing count and link (`:204`).                            | Compact intake summary with stacked mobile layout and clear “View catalog.”                                                                                                                 | Long labels/counts have space at narrow widths.                     |
| Seven-day table shows up to three full login timestamps per row plus “+n more” with no detail interaction (`:289`, `:330`).  | Main table shows login count/most recent login and comparable activity counts; an expandable row exposes the already available full timestamp list.                                         | Uses existing data while keeping row scanning efficient.            |
| Admin selector scopes activity only, but sits deep down the dashboard (`:272`).                                              | Place it next to the Activity title with explicit “Activity for [gallery]” label; avoid claiming it changes all dashboard data.                                                             | Prevents a misleading global gallery context.                       |

**Proposed layout:** header with permitted actions; three compact metric cells; wide Recent proposals/work queue with pending-first visual emphasis only if sorting is based on current statuses; narrow inventory summary; owner/admin activity section beneath. Each proposal row opens its customer sales workspace. No fabricated revenue graph, conversion trend, task assignment, or synthetic “urgency” score.

**Table behavior:** fixed identity/status emphasis, aligned numbers, full timestamps on expansion, sticky header within a clearly scrollable container if needed. Mobile uses user summary cards that expand to activity detail; preserve all fields. Avoid animated row reordering on refresh. A retry sits inside the failed activity region.

**States:** no proposals; no recent uploads; activity empty/loading/error; no accessible galleries; long user name/email; missing dates; high counts; dealer versus owner/admin; gallery switch pending/failure without showing previous gallery's activity as current. Keep scope clearly visible.

## Legal — `/privacy-policy`, `/terms-of-service`

**Preserved job:** make existing policy text readable, navigable, and accessible without signing in. Existing content, section titles, contacts, and effective dates remain unchanged; this is presentation work, not a legal rewrite.

| Before                                                           | After                                                                                                                                       | Why                                                           |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Single long article with no section links (`LegalPage.tsx:176`). | Preserve the restrained document layout; add a desktop section index and mobile “On this page” disclosure using anchor links.               | Readers can find a specific clause quickly.                   |
| Public legal pages use generic gray/blue chrome (`:152`).        | Apply the same paper/ink brand header and readable body typography as entry pages.                                                          | Establishes continuity without adding decorative distraction. |
| Back link always leads to `/` (`:155`).                          | Keep that safe destination; label it clearly and retain cross-links in the footer. If a contextual Back action is added, supply a fallback. | Public and signed-in users can recover predictably.           |

**Layout/states:** 65–75 character reading measure, 1.6–1.75 line height, clear heading spacing, effective date beside title, visible focus and underlined links. Mobile index opens without covering document content. Print styles remove navigation controls and preserve complete content. No entrance animation or scroll-jacking; native anchors respect reduced motion.

## Implementation checks and open decisions

- These are proposals, not new API requirements. Detailed gallery selection, role guards, and customer names must use verified existing sources.
- Confirm approved brand mark, artwork imagery, and whether a serif font may be bundled; system serif is a dependency-free prototype fallback.
- Preserve diagnostic version visibility, all authentication request branches, and legal text while changing their presentation.
- Check 320/390px mobile, tablet, desktop, 200% zoom, keyboard-only navigation, and reduced motion. Stress long artwork titles/emails, zero/one/high counts, missing dates, failed images, and failed saves.
- User-facing errors and focus management are functional parts of the redesign. Production changes require focused tests for the corrected collection deep link, login phases, onboarding retry, role-specific navigation, and proposal destinations.
